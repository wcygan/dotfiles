# Code generation: build.rs vs buf vs protoc plugin

Three supported paths. They produce equivalent output — pick on workflow, not
capability.

## Decision matrix

| Use | When |
|-----|------|
| `connectrpc-build` in `build.rs` | Default. Single-language Rust repo, `.proto` lives next to the crate, no checked-in generated code. |
| `buf generate` | Polyglot repo (Rust + TS + Go + ...), checked-in generated code, you already use `buf` for lint/breaking. |
| `protoc-gen-connect-rust` directly | You have an existing `protoc` invocation (Bazel, Make) and want to plug in a Rust output. |

When in doubt, start with `connectrpc-build`. It's the path the guide uses
and the one with the least moving pieces.

## Path 1 — connectrpc-build (default)

```toml
# Cargo.toml
[build-dependencies]
connectrpc-build = "0.3"
```

```rust
// build.rs
fn main() {
    connectrpc_build::Config::new()
        .files(&["proto/greet.proto", "proto/orders.proto"])
        .includes(&["proto/", "third_party/proto/"])
        .include_file("_connectrpc.rs")
        .compile()
        .unwrap();
}
```

Then in your crate:

```rust
include!(concat!(env!("OUT_DIR"), "/_connectrpc.rs"));
```

Pros: zero extra tooling. Cons: rebuilds cost compile time on every `.proto`
change; CI without `protoc` available won't build (most images include it).

## Path 2 — buf generate

```yaml
# buf.gen.yaml
version: v2
plugins:
  - remote: buf.build/anthropics/connect-rust  # or local: protoc-gen-connect-rust
    out: gen/rust
    opt:
      - emit_views=true
```

```bash
buf generate
```

Then `mod gen;` in your crate root and reference the generated modules.

Pros: language-agnostic, lint/breaking-change checks via `buf`, generated code
is reviewable in PRs. Cons: requires `buf` toolchain, code review noise on
schema changes.

## Path 3 — protoc-gen-connect-rust directly

```bash
cargo install --locked connectrpc-codegen   # provides protoc-gen-connect-rust
protoc \
  --connect-rust_out=./gen/rust \
  --proto_path=./proto \
  proto/greet.proto
```

Use only if you already have a `protoc` build orchestrated elsewhere
(Bazel `proto_library`, Make rules). Pre-built binaries ship from GitHub
releases with SHA-256 checksums + Sigstore signatures — prefer those over
`cargo install` for CI determinism.

## extern_path and well-known types

When the same proto type is generated by another build (e.g. `google.protobuf.Timestamp`
or your own shared types crate), use `extern_path` to remap instead of duplicating:

```rust
connectrpc_build::Config::new()
    .extern_path(".google.protobuf", "::well_known_types::google::protobuf")
    .files(&["proto/greet.proto"])
    .compile()
    .unwrap();
```

**Caveat:** mapped types cannot have view impls emitted on them due to Rust's
orphan rule. Your service trait will fall back to owned messages on those
fields. See `gotchas.md` for the full picture.

## Generated artifacts

Each `.proto` produces, per service:

| Item | What it is |
|------|------------|
| `Foo` (message) | Owned proto struct, `#[derive(Default)]`, all fields public |
| `FooView<'a>` | Borrowed view — fields are `&'a str` / `&'a [u8]` / nested views |
| `FooServiceClient` | Generated client (`client` feature) |
| `FooService` (trait) | Generated server trait — implement on your handler struct |
| `FooService::register` (extension method) | Mounts handlers onto an `axum::Router` |

Buffer types come from `buffa`, the underlying zero-copy proto library. You
do not depend on `prost` directly.
