Explainers and diagrams

Animated graph data flow

A starter for explaining propagation, routing, dependency graphs, fanout, retries, or state machines where seeing data move across edges teaches more than a static box diagram.

  • Primary intent: graph-based explanation
  • Interaction: CSS motion with static fallback
  • Output: data-flow intuition
  • Featured edges: A-B, B-D, B-E, C-E, C-F

Relay rule per hop

  1. A sends one packet into the mesh. Edges make the fanout visible without a paragraph of prose.
  2. B relays to D and E while TTL decreases. The graph shows where work multiplies.
  3. C also tries E. E checks recent packet IDs and drops the duplicate instead of relaying again.
  4. C relays to F. Quiet edges stay visible so the reader understands there are more possible paths.

Use when

  • A topology matters: graph algorithms, mesh routing, queues, dependencies, fanout, retries, replication, or event propagation.
  • The reader needs to see direction, concurrency, duplicate paths, or state transitions.
  • A static flowchart would hide why a node, edge, or repeated visit matters.

Borrow

  • Labeled SVG nodes and edges with muted inactive topology.
  • Animated strokes only on data-carrying edges, with delays or labels when sequence matters.
  • Adjacent rule/state panels: TTL, visited set, queue depth, lock state, cache hit, or retry count.

Avoid

  • Decorative motion that does not encode direction, timing, state, or causality.
  • Animating every edge at once when only a few edges explain the behavior.
  • Hiding conclusions behind animation. The static labels and legend should still teach the idea.

Validation

  • Confirm the active edges are the intended ones, especially named edges like A-B, B-D, B-E, C-E, and C-F.
  • Browser-check desktop and narrow viewports for label overlap, clipped SVG, and horizontal overflow.
  • Check prefers-reduced-motion still leaves a readable graph.
